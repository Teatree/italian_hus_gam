## Commands

```bash
npm install
npm run dev          # Vite dev server at http://localhost:5173
                     # VITE_ADS_ENABLED=1 npm run dev shows the two reserved ad slots (off by default)
npm run build        # tsc --noEmit type-check, then vite build -> ./dist
npm run preview      # serve the production ./dist build locally
npm run images:webp  # convert property photo-*.png -> .webp and photo-*.mp4 -> animated .webp, in place
                     # (sharp + ffmpeg; --keep, --dry-run, --force)

# Authoring-time only (not part of the build):
node scripts/autofill-config.mjs src/properties/<YYYY_MM>/<DD_MM_YY> # fill coordinates/soldPrice/draft facts from idealista
node scripts/fetch-photos.mjs src/properties/<YYYY_MM>/<DD_MM_YY>    # download a property's photos from idealista
node scripts/preview-shot.mjs src/properties/<YYYY_MM>/<DD_MM_YY>   # screenshot that property's page -> preview.webp (--mobile)
```

There is no test suite, linter, or formatter configured. `npm run build` (which runs `tsc --noEmit`) is the only automated check — run it to verify type-correctness after changes.

`convert-images.bat` at the repo root is a double-click wrapper for `npm run images:webp`.

**Image conversion (`scripts/png-to-webp.mjs`)** — one command handles both kinds of source file under `src/properties/`: `photo-N.png` → `photo-N.webp` via sharp (quality 80, max width 1280; the `.png` is deleted unless `--keep`), and `photo-N.mp4` → an **animated** `photo-N.webp` via **ffmpeg on PATH** (`fps=16`, libwebp `-q:v 55`, max width 1000, `-loop 0 -an`; tunables at the top of the script). The video pass runs second, needs ffmpeg only when a clip is present (otherwise it warns and skips), always **keeps the `.mp4`** as the re-encodable master, and skips any clip whose `.webp` is already newer than it — pass `--force` to re-encode anyway. It warns when one clip encodes past 4 MB, since every frame of an animated webp costs bytes. Only `photo-*.mp4` counts as a gameplay clip.

## Architecture

A fully static Vite + React + TypeScript daily-puzzle game (no backend of our own), called **Guess My Casa** (it was *Guess The House* until the November 2026 redesign; `REDESIGN-NOTES.md` has the old → new map, the deliberate deviations from the design handoff and how it was verified). Players guess an Italian house's asking price in up to `MAX_TRIES` (6) guesses; each wrong guess reveals one more photo and one more clue. A guess wins if it's within the **win margin**: ±`TOLERANCE` (10%) of the price. Wrong guesses get a directional arrow, doubled ("way off") past `FAR_THRESHOLD` (30%). Both margins are pure percentages of the price (there are no absolute-euro caps). All of these knobs live in `src/admin.ts`; the pure comparison logic is `evaluateGuess` in `src/game/logic.ts`.

The data flow is **content folders → build-time auto-discovery → date-based scheduling → page shell (`App`) → single-game React tree (`Game`)**:

- **Content as folders (`src/properties/<YYYY_MM>/<DD_MM_YY>/`)** — Each puzzle is a folder containing `config.json` (`coordinates`, `mapZoom`, `soldPrice`, `propertyUrl`, `facts[]`, plus optional per-date theming `titleIcon`/`titleIconUrl`/`shareFlag` (defaults in `src/admin.ts`; `titleIcon`'s filename now only *names the country* — see theming below — and `titleIconUrl` is the "bonus link"), an opt-in `priceVerdict` flag (price-verdict sheet, see game state below), an optional `place` for that sheet, and an authoring-only `prop_pictures` map) plus `photo-*.webp` images (the discovery glob also accepts `png/jpg/jpeg/avif`). Adding a puzzle means creating a folder; there is **no registration step and no code change**. The property's own folder name is the slug — the `<YYYY_MM>` parent (e.g. `2026_06/`) exists only so folders sort chronologically in a file explorer and is never part of the slug. Drop raw `photo-*.png` files and run `npm run images:webp` to convert/downscale them. A photo slot can also be an **animated webp** (renders in the normal `<img>`, auto-plays and loops as soon as that try is reached) — drop a `photo-N.mp4` clip in the folder and the same `npm run images:webp` encodes it (the leftover `.mp4` is kept as the master, is ignored by the discovery glob, and never ships).

- **Photo fetching (`scripts/fetch-photos.mjs` + per-folder `2_run-fetch.bat`)** — Authoring-time helper that downloads a property's photos straight from its **idealista** listing instead of manual screenshots. `config.json`'s `prop_pictures` maps each local slot to an idealista *foto* number (`{ "1": 12 }` → `photo-1` from `…/foto/12/`); the script reads the foto page's `og:image` (ground truth for that photo), pulls the full-res image from the CDN, and saves `photo-N.png` at 1537×1023, **replacing any same-named `photo-N.*`**. It drives a **visible** Chrome via `playwright-core` (channel `chrome`) because idealista's **DataDome** blocks plain fetches and may show a one-time slider the human solves; a persisted profile lives at `scripts/.pw-chrome-profile` (gitignored). It does **not** convert to webp — that stays `npm run images:webp`. `prop_pictures`/the `.bat`s are ignored by the app at runtime.

- **Config autofill (`scripts/autofill-config.mjs` + per-folder `1_autofill.bat`)** — Authoring-time helper that fills `config.json` from the idealista listing named in `propertyUrl`: `coordinates` (from the listing's Google static-map `center=`, captured off the network), `soldPrice` (parsed from the price), and a **draft** `facts[]` (location subtitle, m², rooms/baths, year, floors, land plot, garden/pool) following the existing configs' wording — plus one **measured** fact: free-flow car time to the best nearby city (e.g. `1h 20m to Venice by Car`), computed from the coordinates via the free OSRM demo server, and skipped entirely when the property is already in/near that city (under 20 min drive), when nothing is within 150 min by road, or when routing fails. **The city is scored, not just the nearest one** (`scripts/drive-time.mjs`): every place >= 20k population in `scripts/big-cities.mjs` (generated from GeoNames by `scripts/generate-big-cities.mjs` — re-run it to change the threshold or add a country) is a *candidate*, a shortlist of ~12 is built (nearest 8 by air **plus** the nearest 4 regional/provincial capitals within 150 km, so an important city just over the horizon is not crowded out by small towns), all of them go into one OSRM `table` request, and the winner is the lowest `drive minutes − prominence bonus`. The bonus is GeoNames administrative rank (`PPLC` +90, `PPLA` +60, `PPLA2` +35, `PPLA3` 0, `PPL` **−25**) plus a log-scaled population term, read as "minutes of extra driving this place is worth". Rank is a free proxy for amenities — an Italian `PPLA2` is the provincial capital, with the hospital and university — and the `PPL` penalty is what stops a *frazione* of the property own comune from winning. Tune the constants at the top of `drive-time.mjs`. It always writes exactly 6 facts in **randomized order**: slot 0 is always the location fact; the other 5 slots go to the priority facts (living space, built-in year, drive time) whenever available plus a random draw of the rest, shuffled — facts that lose the draw are logged so you can swap them in — padded with `<INSERT HINT HERE>` for anything it couldn't find. Preserves all other fields and writes 2-space JSON with `coordinates` inline. Same visible-Chrome + DataDome-slider flow as the fetcher; the output is a draft to finalize. (The `.bat`s are numbered `1_`/`2_`/`3_` to suggest the order: autofill, fetch photos, then optionally preview.) **Both scripts refuse to run if another property already uses the same listing** — `scripts/duplicate-url-check.mjs` scans every other `config.json` and compares by idealista listing id (so trailing slashes or language prefixes don't hide a duplicate), stopping with a warning that names the offending folder(s). The technique behind both scripts (anti-detection Chrome launch, human-solved challenge wait-loop, DOM/network/meta extraction, plain-fetch CDN downloads) is written up as a site-agnostic playbook in `WEB-AUTOMATION-GUIDE.md` — read it before modifying these scripts or automating a different site.

- **Preview screenshots (`scripts/preview-shot.mjs` + per-folder `3_preview.bat`)** — Authoring-time helper that shows what a scheduled house's page will look like without waiting for its date. It boots a throw-away Vite dev server with `VITE_OVERRIDE_SLUG=<slug>` (and `VITE_ANALYTICS_URL=''`, so preview runs never append rows to the sheet) on a free port, opens it in headless Chrome via `playwright-core`, waits for every photo and map tile to settle, and writes a full-page screenshot next to `config.json` as **`preview.webp`** (`--mobile` → `preview-mobile.webp` at a phone viewport; `--show` renders in a visible browser). `src/admin.ts` layers that env var on top of the hand-edited `MANUAL_OVERRIDE_SLUG`, which still wins — the variable only exists inside this script's own dev server, so a future puzzle can never leak into a real build. The output is purely for eyeballing: nothing in the app reads it (the discovery glob only matches `photo-*`) and both preview filenames are gitignored.

- **Auto-discovery (`src/properties/index.ts`)** — Uses Vite's `import.meta.glob` (eager, recursive `./**/`) to collect all `config.json` files and all `photo-*` images at build time into a `properties` registry keyed by slug (the config's direct parent folder, whatever its depth). Images are sorted by filename (numeric-aware), so `photo-1 … photo-6` order matters. The folder name slug doubling as a `DD_MM_YY` date is what links content to the schedule. `houseNumber(slug)` is the house's 1-based position among all date-named folders, oldest first — the "Nº 147" in the header chip — so it needs no authoring, and back-filling an earlier empty date shifts every later number.

- **Scheduling (`src/game/schedule.ts` + `src/admin.ts`)** — `getScheduleInfo()` computes the current puzzle's `dateKey` (as `DD_MM_YY`) and the `nextResetMs` boundary. A "puzzle day" runs from `RESET_HOUR` (10:00) in `RESET_TIME_ZONE` (`Europe/Kyiv`, DST-aware) until the same time next day. The zone math is done manually via `Intl.DateTimeFormat` to handle DST correctly — do not replace it with naive `Date` offset arithmetic. `OVERRIDE_SLUG` in `admin.ts` forces a specific property regardless of date (testing only).

- **App shell (`src/App.tsx`)** — Resolves `slug = OVERRIDE_SLUG ?? pastDay ?? dateKey`, looks it up in `properties`, and frames the page: full-bleed `Awning`, then one centred column (max 440px on every screen size) holding the `Header` and either `<Game>` or, when no house is scheduled, the `NoCasa` card (countdown plus a "Play yesterday's casa" link if yesterday had a house). The header carries the title, the theme toggle, the "?" button (opens the how-to-play sheet, whose open state lives here) and the meta row: a flag chip — "Casa Nº 147 · Italia", which is also the bonus link — and the countdown. **Day links (`src/game/dayLink.ts`):** the share text links to `?day=<slug>` (not the bare site), so a link shared on the 10th still opens the 10th's house on the 11th. `pastDay` honours that param only for an existing puzzle dated *strictly before* today — a future date (peeking), today's date, or garbage is dropped and stripped from the address bar via `history.replaceState`, falling back to today's house. While a past day is shown, `PastDayBanner` (sticky, edge to edge, accent-coloured, `--z-sticky` 1050) names the date with a "Today's casa →" link, the meta row shows the date instead of the countdown, the result card drops its countdown, and the reset-time reload is skipped. Analytics rows for it carry that day's slug as `puzzleDate`. A 1s interval (plus a check when the tab becomes visible again) reloads the page when `nextResetMs` passes so a new puzzle loads cleanly. The `<Game>` component is keyed by `property.slug` so changing the active property forces a clean remount with fresh state. The root wears `no-anim` for its first two frames (`useBooting`), so nothing transitions on first paint.

- **Game state (`src/Game.tsx`)** — All gameplay state (`guesses`, `status`, `selected`, `verdict`) lives here, initialised synchronously from `localStorage` so a returning player's game is in place on first paint. `evaluateGuess`/`percentOff`/`revealedCount` (`src/game/logic.ts`) are pure helpers, as are price parsing/formatting (`src/game/format.ts`) and the share text/clipboard logic (`src/game/share.ts`). Progress persists **per slug** (`src/game/storage.ts`, key prefix `gth:v1:`; the format is unchanged from before the redesign), so each house keeps its own saved result and switching houses starts fresh. The number of revealed photos/clues is derived from the count of *wrong* guesses, not total guesses. Page order: `Photo` (clue pill above a 4:3 frame) → `TryCircles` → `GuessForm`, replaced by `ResultCard` once the game ends → `CluesPanel` → `MapView` → optional ad slot → footer. **Two rules to keep:** (1) the price never reaches the page before the game is over — it is only handed to `ResultCard`, `VerdictSheet` and the share builder, which exist only once `isOver`; a locked clue's text isn't rendered either. (2) Everything celebratory is started by the guess that ends the game, inside `handleSubmit` — never by a render or an effect on `status` — so a finished game restored from storage just appears in its final state and nothing replays on reload: confetti in the country's flag colours on a win (plus a centre burst on an *exact* guess, and the unused tries going quiet 2s later), a thumbs-down rain on a loss (`src/fx/celebrate.ts`), the form leaving and the result card rising with a stamped title and a price count-up, and the remaining clue shutters opening 450ms apart. Once the game ends the photo is a **carousel**: prev/next arrows fade in (plus touch-swipe), and it auto-advances one photo every 5 seconds from the photo the player finished on, wrapping 6 → 1; any navigation — arrows, swipe, try circles, clue tiles — rebuilds the interval, so manual browsing resets the cycle rather than stopping it. It holds while the zoom or any sheet is open or the tab is hidden, and never runs under reduced motion. In `Photo` two stacked `<img>` layers are driven through refs: the incoming photo is decoded first, then crossfaded in (400ms in play, 700ms in the carousel). On properties with `priceVerdict: true`, pressing Share detours through `VerdictSheet` (thumbnail, price, place, Steal / Fair / Rip-off). A vote is saved with the game forever, appended as a `🧾 My verdict: ||…||` line to the share text (opinion only — never a euro amount; the `||…||` is Discord/Telegram spoiler markup so the verdict doesn't hint at the price for recipients), and recorded in the `verdict` column of the analytics Results row (which flushes on share, at the vote). Skip, a tap outside, Escape or a drag-down still copies the text, just without a verdict line, and is **not** remembered — the sheet returns on every Share until the player actually votes. The clipboard write happens inside the vote/skip tap so the browser still sees a user gesture; the "Copied!" button state and the toast follow once the sheet has closed (~740ms after a vote). If the browser refuses the copy, `CopySheet` opens with the text selected. `GuessForm` rejects — with a shake and a helper message, costing no try and sending no analytics row — a price under `MIN_GUESS` and a price already guessed.

- **Theming (`src/styles/tokens.css`, `src/theme/`)** — `tokens.css` is the single source of truth for every colour, size, radius, z-index and easing; `src/styles/app.css` (ported from the handoff's reference prototype) and Tailwind's theme (`tailwind.config.js`) only reference its variables — never put a raw hex or a Tailwind palette colour in a component. Three attributes on `<html>` select the values, all applied by `useTheme` (`theme.ts`): `data-theme` = `dark` (the default for everyone, whatever the OS says) or `light` (the sun/moon toggle; saved as `gmc-theme`; an inline script in `index.html` applies it before the CSS so there is no flash); `data-country` = `it|es|pt|fr|gr|fi` from `countryOf()` (`country.ts`: the `titleIcon` filename `<country>_icon.png`, else the `shareFlag`, else Italy), which sets the accent, the shutter colour, the CSS flag, the chip text ("Maison Nº 12 · France") and the confetti colours — but never the share flag (the 🇮🇪 is a running joke); and `data-season`. **Seasons (`season.tsx`)** are data: a token block plus optional extras (title font, a glyph replacing the clue magnifier, confetti and rain glyphs, a photo flicker, a map pin, decoration layers). `activeSeason(slug, todayKey)` needs the house's date inside the season's window *and* the live puzzle day on/before its last day, so from the reset after the last day a season is off everywhere — past-day links and `OVERRIDE_SLUG` included — with no code change (the App's reset reload stays armed on a themed past-day page so an open tab drops it too). A season is dark-only: the page is forced dark and the toggle hidden, the saved preference untouched. Halloween (`HALLOWEEN_FIRST_DAY`..`HALLOWEEN_LAST_DAY` in `admin.ts`, currently `27_10_26`..`31_10_26`; its pieces are in `halloween.tsx`) is the only one: purple palette with a pumpkin-orange accent, Creepster title font (Google Fonts link injected only while active), cobwebs under the awning and in the photo, a drifting fog bank, a candle-flicker on each new photo, 🕯️ in place of the magnifier, a jack-o'-lantern map pin on a night map, 🍬🍭🎃 win confetti and a 👻🦇💀 loss rain. Decorations sit behind the column and ignore the pointer. Fonts (Fraunces, Manrope) are self-hosted in `public/fonts/`.

- **Analytics (`src/analytics.ts`)** — Fire-and-forget POSTs to a Google Apps Script web app that appends rows to a Google Sheet (tabs: `Sessions` one per page load, `Guesses` one per guess, `Results` one per finished game). Every call must swallow errors and never block or break gameplay. The POST uses `Content-Type: text/plain` deliberately — it keeps the request "simple" so there's no CORS preflight (which Apps Script can't answer); don't change it to `application/json`. The `Results` row is buffered in a ref and flushed exactly once (on share, `pagehide`/`visibilitychange`, or unmount) so the `shared` flag can be recorded without duplicate rows. Geo comes from ip-api.com's free endpoint, which is **HTTP-only** — on the deployed HTTPS site it's blocked as mixed content, so ip/country/city are empty in prod (works on local dev). The endpoint URL can be overridden via `VITE_ANALYTICS_URL`. (Note: the root-level `ANALYTICS-SPEC.md` describes a *different* project's analytics — it does not document this pipeline.)

- **Components (`src/components/`)** — `Header` (+ `Awning`), `PastDayBanner`, `Countdown` (pauses while the tab is hidden, recomputes on return), `Photo` + `CluePill` (the clue for the photo on screen; its text swaps, and a new clue replays the pill's entrance and the magnifier's wiggle), `TryCircles` (the six tries, which are also the guess history: arrow or check inside, value underneath; reached tries are tappable to review that photo), `GuessForm`, `ResultCard`, `CluesPanel` (collapsed on every visit; always six fixed-height tiles so the page never changes height when a clue unlocks; locked clues sit behind shutters that swing open), `MapView` (Leaflet/OpenStreetMap; an accent-coloured `divIcon` pin styled from the tokens; the dark-mode filter on the tile pane only; the mouse wheel zooms only after the map is clicked or focused), `Ads` (two reserved slots, rendered only when `ADS_ENABLED`), `NoCasa`, `Icons` (every icon is inline SVG), and the overlays: `Zoom` (full-screen photo with a FLIP open/close out of the page photo), `Sheet` + `Sheets` (bottom sheets: how to play, price verdict, copy fallback) and `Toast`. **Overlays are rendered in portals on `<body>`** because the column is its own stacking context (which also contains Leaflet's z-indexes up to 1000); they use the layer tokens (sticky 1050, anchor ad 1100, fx 1150, scrim 1200, sheet 1210, zoom 1220, toast 1300). Each is a modal dialog: focus moves in and is trapped, Escape closes, the page behind can't scroll, and focus returns to the opener (`src/lib/motion.ts` holds these helpers plus the reduced-motion checks). **Motion** is CSS wherever possible (keyframes and transitions in `app.css`, timings named at the top of `Game.tsx`); every effect honours `prefers-reduced-motion` (no confetti, rain, count-up, slides or autoplay; colour and opacity changes remain).

## Key invariants when editing

- Provide **6 images and 6 facts** per property (`MAX_TRIES`). Gameplay images must be named `photo-N.*` — that prefix is what the discovery glob matches, so anything else in the folder is ignored. Facts reveal one-per-wrong-guess in array order; the *last* facts/photos are the most revealing.
- `soldPrice` is the answer and is never placed in `facts` — it's only shown on the end screen. The share text likewise reveals the closest guess's % off but never a euro amount.
- To schedule a house for a date, the property folder name **must** be `DD_MM_YY` (e.g. `08_06_26`), conventionally placed under a `<YYYY_MM>` month folder for tidy sorting (the month folder has no runtime meaning). Non-date folder names (e.g. a demo property) are only reachable via `OVERRIDE_SLUG`.
- The price must not appear anywhere in the page — markup, attributes, accessible names, a count-up's start value — before the game is over. Keep the price out of every component that renders during play.
- Nothing animates on first paint or when a game is restored, and celebrations never replay on reload: trigger them from the guess, not from state.
- Saved games (`gth:v1:<slug>`) must stay readable: only ever add optional fields. The only other keys are `gth:analytics:seen` (analytics) and `gmc-theme` (the theme choice).
- Colours, sizes, layers and easings come from `src/styles/tokens.css`. Anything that must cover the map goes in a portal on `<body>` with a layer token above 1000.
- Every existing analytics call (`Sessions`, `Guesses`, `Results`) keeps its fields; a rejected guess (typo or repeat) sends nothing.
- The jokes are intentional: "You suck!", "Look how much I suck!", the 🇮🇪 share flag and the "Italian 🥐 house" description.
